# 11 怎样证明「这是我自己做的」

> 先说结论：**不要试图证明「我没用 AI」**，那既做不到也没必要——赛题允许 AI 辅助。
> 你要证明的是三件事：
> 1. **架构和设计是我定的**（不是让 AI 随便生成一个塔防）
> 2. **我能讲清每一行为什么这么写**
> 3. **有相当一部分是我亲手写的、亲手调的**
>
> 这三件事都有「物证」，比嘴上说有用一百倍。下面就是怎么造这些物证。

---

## 一、评委真正会看什么

| 评委动作 | 他在判断什么 | 你要准备的 |
|---|---|---|
| 翻 GitHub commit 历史 | 是不是最后一天一次性上传的 | 每天 1~3 次小 commit，跨度覆盖整个周期 |
| 随手点开一个脚本问「这行干嘛的」 | 你是不是真读过 | 能讲清主流程（见 `07_答辩与代码讲解卡`） |
| 问「这个 bug 你怎么解决的」 | 有没有真实开发过程 | `Docs/Bug记录.md` 里的真实案例 |
| 问「为什么这么设计」 | 有没有自己的判断 | `Docs/设计决策.md` 里的取舍 |
| 让你当场改一个数值/加一个功能 | 会不会真的写代码 | 提前练过 2~3 次 |

**最致命的不是「你用了 AI」，是「你讲不出自己项目里的任何细节」。**

---

## 二、三种「物证」，按可信度排序

### 物证 1：真实的时间线（最硬）

一次性上传 300 个文件的仓库，和「三周里 40 次提交」的仓库，一眼就能分辨。

**做法**：从今天起，每次干完一小块就提交，message 写清「做了什么 + 为什么」。

```powershell
git commit -m "feat: 加入击杀数统计与 HUD 显示"
git commit -m "fix: 暂停时敌人仍在减速计时，改为在 Time.deltaTime 为 0 时跳过"
git commit -m "refactor: 把塔的索敌抽到 EnemyRegistry，避免每帧物理查询"
git commit -m "balance: 重甲兵护甲 7→9，第 3 波箭塔完全打不动，被迫改冰塔"
```

> 注意最后一条：**改数值也是有效提交**。平衡性调整是纯人力活，AI 替不了你去试玩 20 遍。

### 物证 2：你自己写的那部分代码（最有说服力）

如果全部代码都是 AI 写的，你至少要有 **3~5 个「从零自己写」的功能**。见 `12_自己动手任务清单.md`——
里面 8 个任务，挑 4 个做完，你的贡献就不是「改了几个字」，而是「加了 4 个系统」。

### 物证 3：调试记录（最像真人）

AI 不会记得你昨晚为什么卡了两小时。**这份记录只有真做过的人才写得出来。**

建 `Docs/Bug记录.md`，每次卡住就记：

```markdown
## BUG-003 敌人从对象池取出来后卡在原地不动
- 现象：第 2 波开始，部分敌人停在出生点，血条满的，也不掉血
- 排查：
  1. 先看 Console —— 没有报错，排除空引用
  2. 加 Debug.Log 打印 Setup 是否被调用 —— 没打印，说明 Setup 没执行到
  3. 回头看 WaveManager.SpawnEnemy —— 发现 enemy 预制体上我挂的是 EnemyHealth 而不是 Enemy
- 原因：预制体组件漏挂，GetComponent<Enemy>() 返回 null，代码提前 return
- 修复：给预制体补上 Enemy 脚本；顺手在 SpawnEnemy 里加了"缺组件就回收并报错"的兜底
- 学到：静默 return 是最难查的 bug，宁可 LogError 也不能安静地什么都不做
```

**这一段的价值超过 500 行代码**——它证明你真的在自己调。

## 三、`README.md` 里放一段「AI 使用说明」

主动写，比被问出来强。放在 README 顶部附近，坦诚但强调你的主导权：

```markdown
## 关于 AI 辅助

本项目在开发过程中使用了 AI 编程助手，使用方式如下：

- **设计由我完成**：三种防御塔的定位（单体/范围/减速）、四种敌人的克制关系
  （重甲→物理减伤、治疗→需要集火）、波次难度曲线，都是我先画在纸上再实现的。
- **代码实现**：核心脚本的初版由 AI 生成，我逐行阅读后做了修改与重构，具体包括：
  - 把敌人拆成 `Enemy`（移动/机制）和 `EnemyHealth`（血量/护甲）两个组件
  - 血条缩放改为同时修正 `localPosition`，不再依赖 sprite 的 pivot
  - 子弹追踪加入 `SpawnId` 判断，修复对象池复用导致「追错怪」的问题
- **我独立完成的部分**：关卡地形与建造区的摆放、全部数值平衡（见 `Docs/平衡记录.md`）、
  UI 布局、音效挑选、以及 `12_自己动手任务清单.md` 中的 N 个功能。
- **AI 没有参与**：素材收集与许可证核对、试玩测试、Bug 复现与定位。
```

> 这段写得越具体，越可信。**「我改了 X/Y/Z」比「我全程自己写」有说服力得多**——
> 后者一听就是假的，前者能对上 commit 记录。

## 四、设计决策记录（`Docs/设计决策.md`）

评委问「为什么」的时候，你要有东西可翻。每次做一个**非显然**的选择就记一条：

```markdown
## ADR-001 为什么用路径点，不用 NavMesh
- 背景：2D 塔防，敌人路线固定
- 选项：NavMesh（要烘焙、要寻路包）/ 路径点数组（自己写 20 行）
- 决定：路径点
- 理由：塔防的乐趣在于「规划好的路线」，敌人不需要绕障碍；路径点可精确控制
  每个拐角位置，也方便我做「拐角覆盖率」的平衡计算。NavMesh 反而会让敌人
  抄近路，破坏设计意图。
- 代价：以后要做「可破坏地形改变路线」就得重写。

## ADR-002 为什么减速取「最强一次」而不是叠加
- 理由：叠加会让多座冰塔把敌人永久冻住，游戏直接失去难度
- 做法：`slowMultiplier = Mathf.Min(...)`，`slowTimer = Mathf.Max(...)`
```

**写满 5 条，你就是这个项目的作者了。**

## 五、答辩时怎么说（背下来）

被问「AI 帮你写了多少」：

> 「架构是我先定下来的，我用纸画了模块图——敌人只管移动和状态，血量单独一个组件，
> 塔通过接口打伤害，UI 只订阅事件不反向依赖。
> 具体函数写法我用 AI 提速了，但每个脚本我都读过、改过：
> 比如原来血条缩放依赖 sprite 的 pivot，我改成同时修正 localPosition，这样换图不用调；
> 子弹追踪加了 SpawnId，因为对象池复用会让它追错怪。
> 你随便指一个脚本，我可以讲它的主流程；也可以现在现场改一个数值给你看效果。」

**三个动作让你完全站得住：**
1. 让评委挑一个脚本，你现场改数值 / 加一行日志，跑给他们看
2. 准备 3 个「AI 初版 → 我改成什么样」的真实例子
3. 准备 1 个「我自己写的功能」的完整讲解（含踩的坑）

---

## 六、千万别做这 5 件事

| ❌ 别做 | 为什么 |
|---|---|
| 把所有变量改名、调换函数顺序，假装是自己写的 | 评委看 10 秒就能看出「机械重命名」的痕迹，反而更可疑 |
| 删掉注释和中文说明 | 删了更像机器生成，而且你自己以后看不懂 |
| 最后一天一次性 push 全部代码 | commit 时间线直接暴露 |
| 背稿子讲架构，但被问细节就卡 | 比承认「这块我还没吃透」更糟 |
| 说「这些全是我自己写的」 | 2600 行代码、三周时间、零基础，评委不会信；一旦被戳穿，诚信问题比技术问题严重 |
