# 设计决策记录（ADR）

> 评委问「为什么这么设计」的时候，答案不该是「教程里就这么写的」。
> 每做一个**非显然**的选择，就在这里记一条：背景 → 选项 → 决定 → 理由 → 代价。
>
> 写满 5 条，你就是这个项目的作者了。下面 3 条是本项目真实的设计取舍，可以保留，
> 但**答辩前要能不看稿讲出来**。

---

## ADR-001 敌人路线用「路径点数组」，不用 NavMesh

- **背景**：2D 塔防，敌人沿固定路线走向终点
- **选项**：
  - A. NavMesh / A* 寻路：要烘焙、要引包、敌人会自己找最短路
  - B. 路径点数组 + `Vector2.MoveTowards`：自己写 20 行
- **决定**：B
- **理由**：
  1. 塔防的乐趣是「玩家读懂路线后规划塔位」，路线必须是**设计好且不变**的；
     NavMesh 会让敌人抄近路，破坏"哪里该放塔"的设计意图
  2. 路径点可以精确控制每个拐角 —— 而拐角正是塔防的核心（同一座塔在拐角能覆盖两段路）
  3. 没有寻路开销，性能可控
- **代价**：以后要做「可破坏地形改变路线」得重写；敌人不会绕障碍

## ADR-002 减速效果取「最强一次」，不叠加

- **背景**：多座冰塔同时打一只怪，减速要不要叠加？
- **选项**：
  - A. 叠加：`multiplier *= 0.5` 每命中一次
  - B. 取最强：`Mathf.Min` 取倍率，`Mathf.Max` 取时间
- **决定**：B
- **理由**：叠加的话三座冰塔就能把敌人冻到几乎不动，游戏直接失去难度，
  而且玩家会发现"无脑堆冰塔"是唯一解 —— 这是设计事故，不是策略深度
- **代价**：冰塔的"堆叠收益"变低，需要靠射程和覆盖来体现价值

## ADR-003 敌人拆成 `Enemy` + `EnemyHealth` 两个组件

- **背景**：一开始所有逻辑（移动、血量、死亡、特效、发金币）都在一个脚本里，400 多行
- **选项**：
  - A. 一个 `Enemy` 全包
  - B. 拆成 `Enemy`（移动/状态）+ `EnemyHealth`（血量/护甲/死亡事件）
- **决定**：B
- **理由**：
  1. 血条只关心血量，不该知道敌人怎么走路 → 拆开后血条只依赖 `EnemyHealth`
  2. 治疗技能只需要"加血"，不需要碰移动逻辑
  3. 赛题进阶里明确要求「一个类尽量只承担明确职责」
- **代价**：多一次 `GetComponent`；两个组件之间的初始化顺序要小心（在 `Setup` 里显式传入）

## ADR-004 数值走 ScriptableObject，不写在代码里

- **背景**：三种塔、四种敌人、三关五波，数值一大堆
- **选项**：
  - A. 写成 `const` 或 `switch` 分支
  - B. 每种塔/敌人一个 `ScriptableObject` 资产
- **决定**：B
- **理由**：
  1. 改数值不用重编译，试玩调平衡时快一个数量级
  2. 加第四种塔只要新建资产 + 拖一个按钮，**不用改代码**
  3. 资产有类型检查，拖错编辑器直接报错
- **代价**：资产文件多；新人接手要先搞清哪个资产对应哪个东西（所以命名要统一：
  `Tower_` / `Enemy_` / `Waves_` 前缀）
